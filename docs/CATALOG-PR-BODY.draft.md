# Add Hermes Hands to the plugin catalog

Draft pull request body for NousResearch/hermes-agent, describing plugin 0.2.1 and device package 0.2.0. The catalog entry is `plugin-catalog/hermes-hands.yaml`.

Device non-test files are byte-identical to `7e078a50d3a09066aa3e95c3c1a86a9ec221996b` except `executor.py`: if the agent died before a guardian acknowledgement write, the write could fail and skip job-group cleanup. The guardian loop now uses `try/finally` so an acknowledgement write failure still invokes cleanup for registered job groups; its process identity checks are unchanged. The device version remains 0.2.0, but this pinned build differs from the published v0.2.0 tag.

## What it does

Hermes Hands lets a helper work on a paired Windows or Linux computer from chat while Hermes stays on a Linux or WSL gateway. It registers a terminal backend, so `terminal`, `read_file`, `write_file`, `patch`, `search_files` and `execute_code` run on the device selected for the chat. It adds `hands_screenshot`, `hands_devices` and `hands_checkup`. Once a conversation has used a terminal or file tool, including native server file operations, it cannot switch target. Start a new conversation with `/new`, then `/hands use <target>`; before the first terminal or file-tool execution, any target switch is allowed. Switching pauses while a call is pending; a first attempt that is declined or refused before execution releases that guard. Core keeps per-session file-tool caches and the recorded working folder from the previous machine, and no published seam clears them; see [ask 7](https://github.com/NousResearch/hermes-agent/issues/154264). Witness writes and patches still need full paths.

The device runs a separate agent, the `hermes-hands` Python package from the `device` folder of the same repository. It is not on PyPI yet. It connects out over HTTPS and has no inbound listening port. Requests in both directions are signed with Ed25519 keys pinned at pairing. Device targets fail closed when offline, revoked or unreachable; a device command never falls back to the gateway.

## Witness mode

The person at the computer starts `hermes-hands serve --witness` in an interactive terminal. The console names the helper by the label given at pairing, says the helper can run commands and change files only after approving each one, and asks `Start? Type Y or N, then press Enter:`. Every command appears on the person's screen before it runs. Each screenshot needs session permission and a fresh local answer within 30 seconds. Typing `S` and Enter stops the session. Typing `H` and Enter sends the helper up to three short messages. Sessions end after 30 minutes and leave a text receipt and a signed JSON receipt.

While a witness session is active, the plugin's `pre_tool_call` hook asks the helper to approve every tool call that reaches the device, read only commands included, and blocks every tool outside a short safe list and the approval list. It blocks shell composition, script launchers, shell state builtins, patch directives, non-replace patches, common startup persistence that would outlast the session (startup and autostart folders, shell profiles, cron, registry Run keys, scheduled task creation, systemd enable), and arguments with hidden characters. Text Hermes would redact on the approval card and credential patterns Hands recognizes are refused, including beyond a write preview. Other secrets are shown in cleartext on the card and can run if approved. Ordinary paths such as `keyboard.txt` are allowed. Other logon methods, such as `sc create` or the `UserInitMprLogonScript` registry value, are not on that list and reach the helper's approval. The whole approval text must fit in 300 UTF-16 units after surface escaping and wrapping, or 500 on Telegram after core HTML escaping; a longer call is refused, not shortened. Witness device jobs require a human yes even when approvals are off, yolo mode is on, or an unattended context would approve on its own. Another plugin's `pre_tool_call` hook can change a call after the approval card is built, so Hands compares every command that reaches the device with what the card showed and refuses a mismatch: the exact terminal command, its background launch and its `workdir`, the path and every other argument of a read or search, and the exact bytes of a write, where only the BOM and CRLF line ends of the file being replaced may be kept. A `write_file` or `patch` needs a full path, such as `~/notes.txt` or `/c/Users/sam/notes.txt`, because Hermes can place a relative path in more than one folder. Each execution needs a matching Hands approval; identical bodies in a Desktop batch can consume each other's approvals, with no more executions than approvals. A yes to another plugin's approval card does not count. A `patch` runs only when the file it writes is the file as it is now with `old_string`, found exactly once unless the approved call has `replace_all=true`, replaced by `new_string`: Hands reads the file again on the device to check, and refuses a fuzzy match, no match, or several matches unless `replace_all=true` was approved, with a message that asks for the exact text. A `tool_execution` middleware runs before the hooks, so the card already shows its change. The plugin's own `tool_execution` middleware carries the hook's decision into the device call and records terminal and file-tool use on every target to lock target switching.

Git program-selecting options and their abbreviations are refused on every subcommand unless consumed as option values or after `--`. Recognized Git nested-command carriers and other tool launchers, command-selecting configuration settings, all `alias.*` settings and unknown subcommands that could be aliases are refused. Explicit read-only `git config` query modes and `ssh.variant` remain allowed. Ordinary `git difftool` and `git mergetool`, including `-t`/`--tool`, are accepted for helper approval; difftool's `-x`/`--extcmd` command options, their abbreviations and command-selecting configuration settings remain refused. Explicit template directories for clone and init, and send-email recipient/header commands and its SMTP server option (every value), are refused. Config includes and protocol allowances are refused when set. Existing repository configuration and hooks can still launch programs.

The console shows every device job, including core's one-time shell snapshot setup. Core also runs login startup code and sources and refreshes its shell snapshot under the call's approval. These inherited shell jobs are not separately approved. The exact-execution guarantee covers the approved command and file operations, within that runtime envelope.

The exact-execution check matches core's generated command text exactly, after device path mapping, and fails closed when core's text changes. It rebuilds complete file-tool command candidates from the approved arguments and checks stdin where applicable; it does not accept a prefix or an approved path embedded in a larger script. This deliberately couples the verifier to core's command templates. CI covers Hermes 0.23.1, the supported minimum.

## Rule 12: approvals

Text Hermes would mask on the approval card is refused so the person never sees different text from what runs, for example `token: Optional[str]`. Witness calls refuse text Hermes would mask, non-placeholder quoted credential values, token prefixes, Bearer values, key blocks, password flags, credential URLs and long or high-entropy values, including beyond a write preview; plain words and keyword arguments in a recognised source file, with or without spaces around `=`, are treated as variable references unless another refusal rule matches; in other files and in terminal commands, a bare word assigned to a secret-looking name is refused. Shell files (`.sh`, `.bash`, `.zsh`) still refuse no-space assignments, as do environment-lookup lookalikes such as `os.environXYZ123`. The source-file rule is based on the file extension, so text that looks like configuration inside a source file is treated as source. Keyword arguments whose value is a bare name, such as `token=token` inside `Client(token=token, api_key=api_key)` or `password=True`, can be masked by Hermes' own approval display and are refused so the card matches; the spaced form `password = True` works, but `Client(token = token, api_key = api_key)` is still masked and refused.

The hook never approves anything itself. It returns either block or approve with the full approval text, and sends every approve through Hermes's approval flow. The transport selected with `security.approval.transport` must ask a human; a plugin transport can answer automatically, and Hands counts its response as approval. Session and Always choices on a witness approval do not carry over, because every approval uses a fresh rule key; each Always tap leaves an unused `command_allowlist` entry, which the README tells the owner they can delete. Outside a witness session the plugin adds no approval of its own and Hermes's normal approval rules apply.

## Rule 13: disclosures

- Runs shell commands and file operations on the paired device as its logged in user. That user's files, credentials included, are reachable. Witness mode is not a sandbox, and a compromised helper account or gateway can still command paired devices.
- Long running processes: the relay inside the dashboard process, a help poller in the gateway, and the device agent. On Linux, a process that moves to a new session or process group can outlive a stop or revoke. If the small watcher process the agent starts for each job group has died or stalled for more than a second, a process started late by a background command can also outlive Stop.
- Stored credentials: the device keeps its signing key in the OS keyring with the `keyring` extra, otherwise in an owner only file. The gateway stores device public keys and pairing metadata, and reads its relay seed through a declared `config_schema` secret with `get_secret`.
- Command text in the device console and receipts can include sensitive arguments or file content. Device output logs are removed after 7 days; cleanup runs when `serve` starts and then hourly while it runs.
- Reading a PDF or Office document transfers the whole file to the gateway before extraction, even when a page was requested with `offset` and `limit`. The person's console shows the whole-file transport command. Core can wrap a Hands read refusal in a document-extraction or unavailable-terminal error.
- Screenshots are cached on the gateway; screenshots older than 24 hours are removed when another capture occurs, so the last ones stay until the next capture. They are sent to the configured vision model when described and to the chat platform when delivered.
- `hands_checkup` resolves `example.com` and opens connections to 1.1.1.1, 8.8.8.8 and 9.9.9.9 on port 443.
- Optional `H` help, off unless the owner sets `allow_gateway_injection`, puts quoted device text into a user-role model turn in the saved owner chat. It is a prompt-injection surface.
- No telemetry.
- Hermes's dashboard token seam offers every token route to every token provider, so Hands credentials also pass other plugins' token routes. The README documents the revoked key window and why this needs a core change.

## Rule 9: Hermes internals

`hermes plugins validate` warns about two imports outside the public plugin list: `hermes_cli.dashboard_auth.token_auth.register_token_route`, until core PR 151760 or a successor gives plugins a token route seam, and `tools.environments.local.LocalEnvironment`, which core's terminal environment plugin guide documents. The plugin also overrides BaseEnvironment underscore methods `_run_bash`, `_prepare_command`, `_quote_cwd_for_cd` and `_quote_shell_path`, and defines a `_hermes_sandbox_home` property that core reads and writes. In both Hermes 0.23.0 and 0.23.1, `tools/terminal_tool_backends.py:231` writes that property and `tools/terminal_tool_config.py:191` reads it. These subclass contracts are not on the validator's public list, so the two import warnings do not describe every private coupling. The plugin walks no call frames and does not replace or rebind core functions. Every coupling, with the public seam that would replace it, is listed in [the release hook request](HOOK-REQUEST-ISSUE.md). The lead will update [the posted hook request](https://github.com/NousResearch/hermes-agent/issues/154264) from `docs/HOOK-REQUEST-ISSUE.md` immediately after the release push; the posted issue does not yet reflect this release.

In both Hermes 0.23.0 and 0.23.1, `tools/file_tools.py:328-335` returns the cached `ShellFileOperations` while its environment is alive; `tools/file_tools_read_tracking.py:49` sets the 60-second not-found TTL and `tools/file_tools_read_tracking.py:130` expires it. These cache internals are not on the validator's public list. The local-environment configuration reader is Hands's own `_configured_cwd`; `hands/witness.py` imports `redact_sensitive_text` inside `_secret_problem`, public from Hermes 0.23.1, the supported floor.

## Compatibility

In a witness session, an omitted or null terminal `timeout` for a foreground command becomes one explicit default from the public configuration bridge (180 seconds when unset), shown on the approval card and dispatched unchanged. Preserving the scoped profile default needs a public accessor. A background command has no time limit: in a witness session an explicit `timeout` is refused; leave out `timeout`; press S to stop it. Its approval card shows `background=true` and the no-time-limit statement without a timeout.


CI runs the full automated suite on Hermes 0.23.1; `requires_hermes` is `>=0.23.1` in both the manifest and the entry. The gateway supports Linux and WSL. Devices are native Windows with Git Bash and Linux; macOS devices are not supported. The device installs with `pipx install "git+https://github.com/Ridwannurudeen/hermes-hands-plugin@f5ecec6a4c162e56a33a0f72edc2c6d476bc4afb#subdirectory=device"` (the commit with the guardian cleanup fix, pinned by its full 40 character SHA); screenshots work after that install on a desktop session, with the person's yes for each shot. Witness mode needs an interactive terminal and cannot run as a service.

Witness tests cover single query, cron and unattended approve and deny modes, finite unattended turns, a normal human yes, and secret refusal against core redaction.

## What was tested live

Live checks ran on earlier builds of 0.2.0. A Hermes 0.23.0 gateway in WSL and a native Windows 11 laptop covered pairing, terminal work, byte exact file transfer, timeouts, offline failure, witness consent, screenshot grant and decline, checkup, signed receipts and stop. Linux under WSL2 covered commands, files, timeout, witness consent and stop, receipts and revoke. A public HTTPS test covered pairing, a command, checkup, and offline and revoked refusal in normal mode. An owner run on Telegram covered screenshot delivery, decline, timeout, `H` help delivery and stop.

Not yet tested live on this build: a witness session with the current console wording and approval of every call, a screenshot after a fresh device install, Linux screenshots, a separate native Linux host, and Windows scheduled task logon startup.
