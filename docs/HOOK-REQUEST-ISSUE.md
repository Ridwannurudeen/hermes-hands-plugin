# Hook request: public seams for terminal backend plugins

Text for the next edit of [the posted upstream issue](https://github.com/NousResearch/hermes-agent/issues/154264). It lists every place where Hermes Hands relies on Hermes internals, and the public interface that would replace each one.

**Title:** Plugin seams for terminal backend plugins (token routes, local environment, session cwd, file-tool caches, approval state, hook registry, message injection) and provider-scoped token routes

**Body:**

Hermes Hands is a terminal backend plugin. It runs Hermes's terminal and file tools on a computer the user pairs, while Hermes stays on their gateway, and it adds a witness mode in which the helper approves every tool call that reaches the device. It uses public surfaces wherever it can. The rest is listed here, grouped by what it is for. File references identify the module and function; the evidence lines below were verified on Hermes 0.23.0 and 0.23.1. `hermes plugins validate hermes-hands` prints the current file and line of each private import.

Private core imports that `hermes plugins validate` flags under rule 9:

- `hermes_cli.dashboard_auth.token_auth.register_token_route` (`hermes-hands/__init__.py`, `register`). Ask 1; core PR 151760 proposes `ctx.register_dashboard_token_route`.
- `tools.environments.local.LocalEnvironment` (`hands/environment.py`, the `server` target). Core's terminal environment plugin guide documents it; only the public list misses it. Ask 2.

The plugin also overrides BaseEnvironment underscore methods `_run_bash`, `_prepare_command`, `_quote_cwd_for_cd` and `_quote_shell_path`, and defines a `_hermes_sandbox_home` property that core reads and writes. In both Hermes 0.23.0 and 0.23.1, `tools/terminal_tool_backends.py:231` writes that property and `tools/terminal_tool_config.py:191` reads it. These subclass contracts are not on the validator's public list, so the two import warnings do not describe every private coupling. The plugin walks no call frames and does not replace or rebind core functions. `hands/witness.py` imports `agent.redact.redact_sensitive_text` inside `_secret_problem`; this is public from Hermes 0.23.1, the supported floor, but receives a third private-import warning on 0.23.0. The asks below describe the remaining limits.

1. **A plugin way to mark its own dashboard routes as token routes.** The paired device and the gateway's loopback client call routes under `/api/plugins/hermes-hands/` with a bearer token. Today the only way to opt those exact paths into the token seam is `hermes_cli.dashboard_auth.token_auth.register_token_route(path)`, which is not on the public list. Something like `ctx.register_token_route(path)`, scoped to the plugin's own `/api/plugins/<id>/` prefix, would cover it and keep plugins from marking anyone else's routes.

2. **A public way to get a local environment and the host's configured `terminal.cwd`.** The backend keeps a `server` target that should behave like the built in local backend, so it builds a `tools.environments.local.LocalEnvironment`. Because Hands sets `is_container = True` so device paths stay isolated from the host, core replaces a host-shaped `TERMINAL_CWD` (`/home/...`, `/Users/...`, or a drive path) with `~` before calling `create_environment` (`tools/terminal_tool.py`), so Hands reads `TERMINAL_CWD` through its own `_configured_cwd` configuration reader to restore the host's configured `terminal.cwd` for `server`. A small public factory on the terminal environment provider API that builds the local environment (with the profile's host `terminal.cwd` when none was recorded yet) would replace the local-environment import and this configuration workaround. A public background log poll command builder would let a backend recognise core's own poll; Hands keeps a copy of core's `log_delta_command`, so a change to core's poll shape makes background log reads fail (the job reads as lost) until Hands updates its copy.

3. **A way to notify the owner without starting a turn.** When a paired device's local deny list changes, the relay (running in the dashboard process) refuses that device until the owner accepts the change, and it should tell the owner in their chat. `ctx.inject_message` does not fit: it starts an agent turn, needs `allow_gateway_injection`, only works where a gateway injector is live, and needs a session origin shaped like `SessionSource`, which is not public. A public `ctx.notify_owner(text)` (or a `notify` in `hermes_cli.plugin_events`) that sends a plain message to the profile's home channel from any process would cover it. For now the alert shows in `/hands status` and the Desktop pane.

4. **Token routes scoped to the provider that owns them.** The token seam asks every token provider about every registered token route and accepts the first principal it gets (`hermes_cli/dashboard_auth/token_auth.py`), and the drain route reads only `token_principal.principal`, never its provider or scopes (`hermes_cli/web_routers/actions.py`). So a credential that is valid for one plugin also opens every other plugin's token routes and the drain route. For Hands that means a fresh bearer signed by a paired or revoked device key, an unused pairing code, or the gateway's local bearer passes the token check on routes that have nothing to do with Hands. A revoked key keeps that until 1 hour after the relay first sends its signed stop reply, or 7 days if the device never contacts the relay again. Hands already returns None for anything it cannot verify, but it cannot tell which route it is being asked about, because `verify_token` gets only the token. A token route registration that names its provider, for example `register_token_route(path, provider=...)` or the `ctx.register_token_route` from ask 1 bound to the calling plugin's provider, with the seam asking only that provider, would close it. Checking the provider and scope in the drain handler would close the drain case on its own.

5. **`strip_env_keys` honoured in the terminal's own spawn env.** A backend provider declares `strip_env_keys` so model-authored commands can never read its credentials (`agent/terminal_env_provider.py`). Core applies them to background and helper processes through `_sanitize_subprocess_env` (`tools/environments/local.py`), but `_make_run_env`, which builds the env for every foreground terminal command, passes `frozenset()` instead. Hands keeps a `server` target that is a plain `LocalEnvironment`, so its relay seed would reach `echo $HANDS_RELAY_SEED` on that target. For now Hands passes `env={"HANDS_RELAY_SEED": ""}` to that `LocalEnvironment` itself. Passing `_plugin_terminal_env_strip_keys()` there, as `_sanitize_subprocess_env` does, would make the declared keys enough on their own.

6. **A public read and update of the session's working folder.** A multi-target backend has to tell whether the `cwd` core passes to `execute()` is an explicit `workdir=`, the session's recorded cwd, or a gateway default, so a device never starts in a folder that only exists on the server. When a conversation switches targets or receives a gateway workspace override while on a device, the backend also has to keep core's recorded session cwd pointed at the active target. Hands now keeps each target's last folder itself and never writes core's record. Once a conversation has used a terminal or file tool, including native server file operations, it cannot switch target. Start a new conversation with `/new`, then `/hands use <target>`; before the first execution, any target switch is allowed. An in-flight tool call pauses switching; declining or refusing its first pre-execution attempt releases that guard. See ask 7 for the cache and working-folder limits. A `workdir` equal to another target's last folder is still read as that target's. Public helpers on the environment or context API to read and update the session's recorded cwd (plus passing `cwd` provenance to `execute()`) would let target switches work within a conversation and remove those ambiguities.

7. **Public target-change and file-tool lifecycle seams.** `ShellFileOperations` caches which executables exist and where `rg` is for whichever machine answered first (`tools/file_operations.py`, `tools/file_operations_search.py`), and `tools.file_tools_read_tracking` keeps a 60-second not-found cache and read-dedup hit counters per session. Once a conversation has used a terminal or file tool, including native server file operations, it cannot switch target. Start a new conversation with `/new`, then `/hands use <target>`; before the first execution, any target switch is allowed. An in-flight tool call pauses switching; declining or refusing its first pre-execution attempt releases that guard. Core keeps per-session file-tool caches and the recorded working folder from the previous machine, and no published seam clears them. In both Hermes 0.23.0 and 0.23.1, `tools/file_tools.py:328-335` returns the cached `ShellFileOperations` while its environment is alive; `tools/file_tools_read_tracking.py:49` sets the 60-second not-found TTL and `tools/file_tools_read_tracking.py:130` expires it. These cache internals are not on the validator's public list. Device ripgrep probes still report a miss so searches use grep; searches naming an absolute ripgrep executable are refused on devices, including after `/new`. A public invalidation seam would remove the need to disable device ripgrep. Hands tells a file tool's commands apart by the tool name core passes to its `tool_execution` middleware; a command run outside any tool call, such as the oversized-result spill, is refused on a witness device. A public target-change callback carrying the active environment, `invalidate_file_ops(task_id, session_id)`, and a `file_op=True` marker on file-tool `execute()` calls would remove those workarounds. Together with the cwd seam in ask 6 and coverage for direct host file operations, they would let target switches work within a conversation.

8. **`~` resolved through the environment for plugin backends.** File tools expand `~` with the gateway's own home (`_expand_tilde`, `tools/file_tools_paths.py`), so on a plugin backend whose machine has a different home, a `~/x` path is reported as the gateway user's home in `resolved_path`, even though Hands writes it under the device home. The SSH backend already resolves `~` against the remote's detected home (`_ssh_remote_home` and `_resolve_ssh_path`). Hands currently defines the `_hermes_sandbox_home` property to keep that anchor on the active target. In both Hermes 0.23.0 and 0.23.1, `tools/terminal_tool_backends.py:231` writes that property and `tools/terminal_tool_config.py:191` reads it. A public environment attribute, such as `remote_home`, would replace this underscore contract and fix it for every plugin backend.

9. **A public read of the profile's effective `terminal.backend`.** `/hands use` and `hermes hands doctor` check whether the profile's effective `terminal.backend` is `hands` before letting the user select a device, including when the backend comes from `TERMINAL_ENV` in the profile `.env` or launch environment rather than `config.yaml`. Hands now reads `terminal.backend` from `config.yaml` with `hermes_cli.config.read_raw_config_readonly`, then `TERMINAL_ENV` from the process environment, then from the profile `.env` with `agent.secret_scope.load_env_file`, the order core uses. It cannot see a managed-scope pin, so the check can name the wrong backend in that case; it only words `/hands use` and doctor, and never picks a target. A small public helper (for example `ctx.get_terminal_backend()`) would make it exact. The same seam should expose the effective terminal timeout from the active profile scope: in both tested core versions, `tools/terminal_tool_config.py:270-277` calls the unpublished `tools.terminal_scope.terminal_env`, which reads the isolated scope in `tools/terminal_scope.py:81-86`. The public configuration bridge can report a different timeout from that active scope. For an omitted or null foreground `timeout`, Hands now uses one explicit default from the public configuration bridge (180 seconds when unset), shows it on the approval card, and dispatches it through a public argument-modification hook. Changed execution values still refuse. A public effective-timeout read would preserve the scoped profile default instead of needing this explicit default.

10. **A public query of the approval state.** In a witness session Hands asks the helper to approve every tool call that reaches the device, so it must refuse device tools when nobody will be asked: approvals bypassed for the session, yolo mode, or an unattended context whose mode approves on its own. Hands now records a person's answer from the public `post_approval_response` hook and refuses on the device every job of a witness call that has none, so under yolo or approvals off a device tool passes the gate and is then refused. A public `ctx.approval_state(session_key)` that says whether a `pre_tool_call` "approve" will reach a person would let Hands refuse before the call starts.

11. **Frozen arguments after an approval.** A `pre_tool_call` hook that returns "approve" with a message cannot stop another plugin's `pre_tool_call` hook from changing the call after the person approved what they saw. Hands now rebuilds the complete expected file-tool command text from approved arguments and device path mapping and compares it exactly with the command that will execute, binding command, effective cwd, timeout, stdin, background rewriting and output capture, refusing callbacks and undeclared environment or login overrides. Background polls must name the exact artifact paths retained from the verified launch. For replacement patches it re-reads the current device file to verify the resulting bytes and requires exactly one exact old_string occurrence unless the approved call has replace_all=true. Fuzzy replacements and V4A delete, move or add operations cannot run under a replacement approval. The check fails closed if core changes its generated command text. A guarantee that arguments are frozen once an approval is shown would close that.

12. **Public message injection checks.** Registration starts the help poller whenever a relay seed exists, including in a process without a live gateway injector. A refused injection releases the message lease without spending an attempt and applies backoff; the relay refuses a device message when the owner has not set `allow_gateway_injection`. Hands now uses the result of `ctx.inject_message` and reads `allow_gateway_injection` from the plugin's config entry. Public `ctx.can_inject_messages()` and `ctx.injection_allowed()` would let the poller skip processes that cannot deliver.

13. **Public approval display helpers.** Every approval surface shows the redacted copy of the approval text, so a witness approval whose text redaction would change could show the helper something other than what runs. Hands refuses such calls with the public `redact_sensitive_text` plus its own stricter check: every character must be visible, with no run of 21 spaces. Witness calls refuse text Hermes would mask, non-placeholder quoted credential values, token prefixes, Bearer values, key blocks, password flags, credential URLs and long or high-entropy values, including beyond a write preview; plain words and keyword arguments in a recognised source file, with or without spaces around `=`, are treated as variable references unless another refusal rule matches; in other files and in terminal commands, a bare word assigned to a secret-looking name is refused. Shell files (`.sh`, `.bash`, `.zsh`) still refuse no-space assignments, as do environment-lookup lookalikes such as `os.environXYZ123`. The source-file rule is based on the file extension, so text that looks like configuration inside a source file is treated as source. Keyword arguments whose value is a bare name, such as `token=token` inside `Client(token=token, api_key=api_key)` or `password=True`, can be masked by Hermes' own approval display and are refused so the card matches; the spaced form `password = True` works, but `Client(token = token, api_key = api_key)` is still masked and refused. Ordinary paths such as `keyboard.txt` and recognized programmatic environment-reference expressions in source files are allowed. Because the agent path coerces arguments only after the hook runs, a witness call whose arguments are not already their schema type (`"true"` for `background`, `"50"` for `limit`) is refused and the model resends it. Public exports of `redact_approval_display` and `coerce_tool_args`, or coercion before `pre_tool_call` runs, would lift both limits.

Two smaller questions, no change needed:

1. Rule 11 covers credentials a plugin reads. The device agent is a separate Python package, installed with pipx from the same repository, that keeps its own private key in the OS keyring or an owner only file on the device, and the gateway side stores only device public keys plus one relay seed declared as a `config_schema` secret and read with `get_secret`. Is that the shape you want for plugins with a companion agent?
2. Rule 17 allows a binary a user's machine fetches at setup time from the official source. Do compiled wheels from PyPI that the companion package depends on (psutil, cryptography, mss and Pillow) fall under that, or is anything more expected?

Happy to send PRs for any of these seams. Thanks for the plugin system.
