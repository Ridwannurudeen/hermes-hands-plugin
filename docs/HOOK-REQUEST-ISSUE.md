# Draft issue for NousResearch/hermes-agent (for Ridwan to post on Monday; NOT posted)

**Title:** Plugin seams for terminal backend plugins (token routes, local environment, session cwd, file-tool caches, terminal backend check) and provider-scoped token routes

**Body:**

Hi team,

I'm building Hermes Hands, a terminal backend plugin that runs Hermes's terminal and file tools on a laptop the user pairs, while Hermes stays on their server. It's my entry for the plugin hackathon and it uses public surfaces everywhere it can, except for eight private core modules (eleven symbols across fifteen import sites; the validator prints the first ten sites and "and 5 more") that `hermes plugins validate` flags under rule 9:
- `hermes_cli.dashboard_auth.token_auth.register_token_route` (`hermes-hands/__init__.py:12`),
- `tools.terminal_scope.build_profile_terminal_scope` (`hermes-hands/hands/commands.py:277`),
- `tools.environments.local.LocalEnvironment` (`hermes-hands/hands/environment.py:27`),
- `tools.file_tools_read_tracking.notify_other_tool_call` (`hermes-hands/hands/environment.py:354`),
- `tools.approval.get_current_session_key` (`hermes-hands/hands/environment.py:365,519,637`),
- `tools.terminal_tool`: `get_session_cwd` (`hermes-hands/hands/environment.py:366,520`), `record_session_cwd` (`hermes-hands/hands/environment.py:366,638`), `_get_env_config` (`hermes-hands/hands/environment.py:520`), and `resolve_task_overrides` (`hermes-hands/hands/environment.py:520`),
- `tools.file_tools_paths._configured_terminal_cwd` (`hermes-hands/hands/environment.py:401`),
- `tools.terminal_tool_lifecycle.get_active_env` (`hermes-hands/hands/environment.py:716`),

plus `tools.file_tools.clear_file_ops_cache` (`hermes-hands/hands/environment.py:353,356`), which the static check skips because `hands/tools.py` shadows bare `tools`, and a call-frame check for `tools.file_operations` (`hermes-hands/hands/environment.py:115-124`). I'd rather ask for public seams than keep the private couplings, so here they are.

1. **A plugin way to mark its own dashboard routes as token routes.** The paired device and the gateway's loopback client call routes under `/api/plugins/hermes-hands/` (`hermes-hands/hands/relay.py:34`) with a bearer token. Today the only way to opt those exact paths into the token seam is `hermes_cli.dashboard_auth.token_auth.register_token_route(path)` (`hermes-hands/__init__.py:12,28`), which is not on the public list. Something like `ctx.register_token_route(path)`, scoped to the plugin's own `/api/plugins/<id>/` prefix, would cover it and keep plugins from marking anyone else's routes.

2. **A public way to get a local environment and the host's configured `terminal.cwd`.** The backend keeps a `server` target that should behave like the built in local backend, so it builds a `tools.environments.local.LocalEnvironment` (`hermes-hands/hands/environment.py:27`). And because Hands sets `is_container = True` so device paths stay isolated from the host, core replaces a host-shaped `TERMINAL_CWD` (`/home/...`, `/Users/...`, or a drive path) with `~` before calling `create_environment` (`tools/terminal_tool.py:805-809`), so Hands calls `tools.file_tools_paths._configured_terminal_cwd` (`hermes-hands/hands/environment.py:401,406`; `tools/file_tools_paths.py:106-112`) to restore the host's configured `terminal.cwd` for `server`. A small public factory on the terminal environment provider API that builds the local environment (with the profile's host `terminal.cwd` when none was recorded yet) would replace both private imports.

3. **A way to notify the owner without starting a turn.** When a paired device's local deny list changes, the relay (running in the dashboard process) refuses that device until the owner accepts the change, and it should tell the owner in their chat. `ctx.inject_message` doesn't fit: it starts an agent turn, needs `allow_gateway_injection`, only works where a gateway injector is live, and needs a session origin shaped like `SessionSource`, which isn't public. A public `ctx.notify_owner(text)` (or a `notify` in `hermes_cli.plugin_events`) that sends a plain message to the profile's home channel from any process would cover it. For now the alert shows in `/hands status` and the Desktop pane.

4. **Token routes scoped to the provider that owns them.** The token seam asks every token provider about every registered token route and lets the first principal it gets through (`hermes_cli/dashboard_auth/token_auth.py:57-86`), and the drain route reads only `token_principal.principal`, never its provider or scopes (`hermes_cli/web_routers/actions.py:187-221`). So a credential that is valid for one plugin also opens every other plugin's token routes and the drain route. For Hands that means a fresh bearer signed by a paired or revoked device key, an unused pairing code, or the gateway's local bearer passes the token check on routes that have nothing to do with Hands. A revoked key keeps that until 1 hour after the relay first sends its signed stop reply, or 7 days if the device never contacts the relay again. Hands already returns None for anything it cannot verify, but it can't tell which route it is being asked about, because `verify_token` gets only the token. A token route registration that names its provider, for example `register_token_route(path, provider=...)` or the `ctx.register_token_route` from ask 1 bound to the calling plugin's provider, with the seam asking only that provider, would close it. Checking the provider and scope in the drain handler would close the drain case on its own.

5. **`strip_env_keys` honoured in the terminal's own spawn env.** A backend provider declares `strip_env_keys` so model-authored commands can never read its credentials (`agent/terminal_env_provider.py:37-38`). Core applies them to background and helper processes through `_sanitize_subprocess_env` (`tools/environments/local.py:333-337`), but `_make_run_env`, which builds the env for every foreground terminal command, passes `frozenset()` instead (`tools/environments/local.py:776-787`, used at `:1136`). Hands keeps a `server` target that is a plain `LocalEnvironment`, so its relay seed would reach `echo $HANDS_RELAY_SEED` on that target. For now Hands passes `env={"HANDS_RELAY_SEED": ""}` to that `LocalEnvironment` itself (`hermes-hands/hands/environment.py:411-416`). Passing `_plugin_terminal_env_strip_keys()` there, as `_sanitize_subprocess_env` does, would make the declared keys enough on their own.

6. **A public read and update of the session's working folder.** A multi-target backend has to tell whether the `cwd` core passes to `execute()` is an explicit `workdir=`, the session's recorded cwd, or a gateway default, so a device never starts in a folder that only exists on the server (`hermes-hands/hands/environment.py:514-545`); and when a conversation switches targets or receives a gateway workspace override while on a device, the backend has to keep core's recorded session cwd pointed at the active target (`hermes-hands/hands/environment.py:361-374,633-649`). Today that takes `tools.approval.get_current_session_key` (`:365,519,637`), `tools.terminal_tool.get_session_cwd` (`:366,520`), `tools.terminal_tool.record_session_cwd` (`:366,638`), `tools.terminal_tool._get_env_config` (`:520`), and `tools.terminal_tool.resolve_task_overrides` (`:520`). Public helpers on the environment/context API to read and update the session's recorded cwd (plus passing `cwd` provenance to `execute()`) would replace all five symbols.

7. **Public target-change and file-tool lifecycle seams.** `ShellFileOperations` caches which executables exist and where `rg` is for whichever machine answered first (`tools/file_operations.py:225-227`, `tools/file_operations_search.py:518-591`), and `tools.file_tools_read_tracking` keeps a 60-second not-found cache and read-dedup hit counters per session (`tools/file_tools_read_tracking.py:118-140`). When a conversation switches targets (`hermes-hands/hands/environment.py:350-361,714-728`), Hands drops the old file-operation and read-tracking caches. It calls `tools.file_tools.clear_file_ops_cache` (`hermes-hands/hands/environment.py:353,356`; `tools/file_tools.py:377-400`) and `tools.file_tools_read_tracking.notify_other_tool_call` (`hermes-hands/hands/environment.py:354,359`; `tools/file_tools_read_tracking.py:192-206`). The target-change handler also calls private `tools.terminal_tool_lifecycle.get_active_env` (`hermes-hands/hands/environment.py:716,718`) to identify the active environment before it clears state. Hands walks Python call frames to identify file-tool calls (`_from_file_tools`, `hermes-hands/hands/environment.py:115-124`) because `ShellFileOperations._exec` (`tools/file_operations.py:229-239`) does not mark them when calling `execute()`. A public target-change callback carrying the active environment, `invalidate_file_ops(task_id, session_id)`, and a `file_op=True` marker on file-tool `execute()` calls would replace these workarounds.

8. **`~` resolved through the environment for plugin backends.** File tools expand `~` with the gateway's own home (`_expand_tilde`, `tools/file_tools_paths.py:32-49`), so on a plugin backend whose machine has a different home, a `~/x` path is reported as the gateway user's home in `resolved_path`, even though Hands writes it under the device home. The SSH backend already resolves `~` against the remote's detected home (`_ssh_remote_home` and `_resolve_ssh_path`, `tools/file_tools_paths.py:217-254`). The same lookup through an environment attribute, such as a `remote_home` a plugin environment can report, would fix it for every plugin backend.

9. **A public read of the profile's effective `terminal.backend`.** `/hands use` and `hermes hands doctor` check whether the profile's effective `terminal.backend` is `hands` before letting the user select a device, including when the backend comes from `TERMINAL_ENV` in the profile `.env` or launch environment rather than `config.yaml`. Today that calls `tools.terminal_scope.build_profile_terminal_scope` (`hermes-hands/hands/commands.py:277`; `tools/terminal_scope.py:114-159`), which is private and loads `TERMINAL_*` keys from `.env`. A small public helper (for example `ctx.get_terminal_backend()`) would let backend plugins check whether they are active without importing `tools.terminal_scope`.

Two smaller questions for the record, no change needed for my plugin:

1. Rule 11 covers credentials a plugin reads. My device agent is a separate PyPI package that keeps its own private key in the OS keyring or an owner only file on the device, and the gateway side stores only device public keys plus one relay seed declared as a `config_schema` secret and read with `get_secret`. Is that the shape you want for plugins with a companion agent?
2. Rule 17 allows a binary a user's machine fetches at setup time from the official source. Do compiled wheels from PyPI that the companion package depends on (psutil, cryptography) fall under that, or is anything more expected?

Happy to send PRs for any of these seams if that helps. Thanks for the plugin system, it made this possible without touching core.
